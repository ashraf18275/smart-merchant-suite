# نموذج البيانات والمزامنة السحابية — عدة التاجر الذكي

**الحالة:** تصميم مرحلي مطلوب قبل ربط Flutter بالمزامنة.  
**الهدف:** جعل نموذج Supabase مطابقًا لقواعد المجال المحلية، مع الحفاظ على العمل دون إنترنت ومنع فقد أو تكرار العمليات.  
**قاعدة أساسية:** لا تبدأ مزامنة بيانات البيع والمخزون قبل إكمال نموذج الفروع والمخازن والكميات والدفاتر واختبارات العزل.

## 1. لماذا نحتاج هذه الوثيقة؟

قاعدة SQLite المحلية أصبحت أغنى من نموذج البيانات السحابي الحالي. ربط التطبيق مباشرة بالجداول السحابية الموجودة سيؤدي إلى فقد معلومات تشغيلية مهمة، خصوصًا:
- الرصيد المنفصل لكل مخزن.
- الفرع والمخزن اللذان حدثت فيهما العملية.
- الكميات الكسرية بوحدة الألف.
- العملاء والموردون والدفاتر والمشتريات.
- الدفعات المستقلة والمرتجعات.

لذلك يجب بناء طبقة مزامنة حول عمليات المجال، لا نسخ صفوف SQLite عشوائيًا إلى Supabase.

## 2. القواعد الثابتة

1. `business_id` موجود في كل سجل سحابي تابع لنشاط.
2. كل سجل مكاني يربط بالنشاط والفرع والمخزن بمفاتيح أجنبية مركبة تمنع الخلط بين الأنشطة.
3. المخزون مصدره أرصدة المنتج/المخزن وحركاته، وليس قيمة إجمالية يكتبها العميل.
4. كل عملية بيع أو استلام أو تحويل أو مرتجع تحفظ كوحدة ذرية على الخادم.
5. كل عملية محلية قابلة للمزامنة لها `operation_id` ثابت يولد مرة واحدة ويحفظ في SQLite قبل الإرسال.
6. يعاد إرسال العملية بالمعرف والحمولة نفسيهما؛ استخدام المعرف نفسه بحمولة مختلفة يرفض.
7. لا يطبق `last-write-wins` على المال أو المخزون أو دفاتر الحسابات.
8. لا يحذف أثر مالي أو مخزني؛ التصحيح بعكس موثق.
9. لا ترسل مفاتيح service-role إلى Flutter أو Windows أو Android.
10. لا تعد المزامنة مكتملة حتى تنجح اختبارات جهازين مع قطع الشبكة وإعادتها.

| purchase_items | cloud_purchase_items | غير موجود |

| Returns | cloud_sales_returns / cloud_purchase_returns | غير موجودة |
| Cash shifts | cloud_cash_sessions / cloud_cash_movements | موجودة: فتح/حركة/إقفال وفرق، مرتبطة بفرع وسجل صندوق |

## 4. الكميات والدقة

### الوضع المحلي
- SQLite schema version 7 حوّل الكميات إلى أعداد صحيحة بوحدة الألف.
- 1000 تمثل وحدة كاملة، و250 تمثل ربع وحدة.
- الأموال أعداد صحيحة بوحدات العملة الصغرى، ولا تستخدم floating point.

### الوضع السحابي الحالي
- `cloud_products.stock_quantity` و`cloud_inventory_movements.quantity_delta` و`cloud_product_warehouse_stock.quantity_scaled` أعداد bigint بوحدة الألف.
- `cloud_sale_items.quantity_scaled` bigint بوحدة الألف.
- 1000 = وحدة كاملة، و250 = ربع وحدة؛ لا تستخدم floating point.
- RPCs الجديدة تستقبل الكمية بوحدة الألف، وتحسب إجمالي بند البيع بتقريب half-up صحيح دون double rounding.
- واجهات التوافق القديمة تحول whole units إلى thousandths. لا تستخدمها من عميل جديد إذا كان يحتاج كسور الوحدات.

### قرار المزامنة
- تم تنفيذ توحيد الكميات في الهجرة `20261104006000_cloud_quantity_thousandths.sql`.
- تفحص الهجرة overflow قبل الضرب في 1000، ثم تحول الأرصدة والحركات وبنود البيع مرة واحدة وتعيد بناء بصمات idempotency.
- لا تشغّل هذه الهجرة يدويًا مرة ثانية ولا تعدل بيانات إنتاجية خارج نظام الهجرات. لم يتم تطبيقها على مشروع إنتاجي.
- يظل مطلوبًا اختبار ترحيل على نسخة إنتاجية منزوعة البيانات الحساسة قبل أي تطبيق حي، ومراجعة النسخ الاحتياطي وخطة rollback.

### حالة التنفيذ في 4 نوفمبر 2026

- تم إنشاء الجداول السحابية للفروع والمخازن وأرصدة كل مخزن.
- trigger ينشئ فرعًا ومخزنًا افتراضيين لكل نشاط جديد، كما تم ترحيل الأنشطة الموجودة وقت الهجرة.
- كل منتج جديد يرتبط بمخزنه الافتراضي ويبدأ برصيد مستقل.
- البيع والتسوية يستخدمان RPCs تقبل branch_id وwarehouse_id، وتحدث رصيد المخزن وإجمالي المنتج في معاملة واحدة.
- اختبارات PostgreSQL أثبتت عزل النشاطين واستقلال مخزن ثانٍ عن المخزن الافتراضي، وبيع 1.25 وحدة بإجمالي صحيح 125، وإعادة المحاولة دون تكرار.
- تحقق CI الناجح: https://github.com/ashraf18275/smart-merchant-suite/actions/runs/41751141019
- اختبار الترحيل التاريخي ينشئ قاعدة منفصلة بالهجرات السابقة، يزرع سجل بيع ومخزون بوحدات كاملة، يطبق هجرة الألف، ثم يثبت تحويل 8 وحدات إلى 8000، وبند البيع 2 إلى 2000، والحركة -2 إلى -2000 دون تغيير إجمالي/مدفوع الفاتورة، مع إعادة إرسال آمنة للعملية القديمة.
- لم تنفذ بعد واجهة إدارة الفروع والمخازن أو مزامنة Flutter.

### تحديث نموذج العملاء والموردين — 4 نوفمبر 2026

- أضيفت `cloud_customers` و`cloud_suppliers` مع قيود tenant-scoped.
- أضيفت دفاتر append-only للعملاء والموردين، وأرصدة مشتقة من مجموع القيود.
- RPCs إنشاء العميل/المورد تسجل الرصيد الافتتاحي وتدقيق الإنشاء ذريًا.
- RPCs تحصيل العميل وسداد المورد تحفظ وسيلة الدفع، وتمنع تجاوز الرصيد، وتدعم idempotency keys وبصمة الحمولة.
- RLS تسمح بالقراءة حسب صلاحية الحساب/العميل/المورد، بينما كل الكتابة عبر RPCs؛ لا DML مباشر من التطبيق.
- لا تزال دفعات الحساب غير مرتبطة بدفتر النقدية السحابي، ولا توجد جداول ورديات أو حركات صندوق سحابية، كما لم تُربط فواتير البيع والمشتريات بالدفاتر بعد.
- لا يوجد Flutter Supabase client أو Outbox أو مزامنة فعلية بعد.

## 5. نموذج الفروع والمخازن المقترح

### الكيانات
- `cloud_branches`: `id`, `business_id`, `name`, `is_active`, بيانات الاتصال.
- `cloud_warehouses`: `id`, `business_id`, `branch_id`, `name`, `is_active`.
- المنفذ حاليًا: `cloud_product_warehouse_stock` بأعمدة `business_id`, `branch_id`, `warehouse_id`, `product_id`, `quantity_scaled`, `updated_at`؛ الكمية integer thousandths.
- الاسم الحالي `quantity_scaled` ويخزن وحدة الألف.
- `cloud_inventory_movements`: إضافة `branch_id` و`warehouse_id` و`movement_type` ومرجع المستند والفاعل.

### قواعد النزاهة
- `unique (id, business_id)` على الفرع والمخزن والمنتج.
- المفاتيح الأجنبية المركبة تربط المخزن بالفرع داخل النشاط نفسه، والرصيد بالمنتج والمخزن داخل النشاط نفسه.
- قيد فريد على `(business_id, product_id, warehouse_id)` في رصيد المخزن.
- لا يعدل الرصيد مباشرة من العميل؛ عمليات الاستلام والبيع والتحويل والتسوية RPCs ذرية تكتب الرصيد والحركة والمستند معًا.
- `cloud_products.stock_quantity` الحالي يمكن إبقاؤه مؤقتًا كقيمة تجميعية للتوافق، لكن لا يكون مصدر الحقيقة بعد الانتقال. يحسب من أرصدة المخازن ويزال فقط بعد ترحيل كل المستهلكين.

### التوافق مع البيانات الحالية
- ينشأ فرع ومخزن افتراضيان لكل نشاط قائم.
- تنقل كمية كل منتج الحالية إلى مخزنه الافتراضي دون تغيير إجمالي الرصيد.
- تسند حركات المخزون القديمة إلى المخزن الافتراضي مع الاحتفاظ بسببها وتاريخها ومعرف العملية.
- لا تخمن فرعًا أو مخزنًا لعملية تاريخية إذا كانت البيانات لا تسمح بذلك؛ تستخدم قيمة افتراضية موثقة أو تترك الحقل nullable وفق قرار ترحيل واضح.

### ما نُفذ حتى الآن (4 نوفمبر 2026)

- أضيفت `cloud_branches` و`cloud_warehouses` و`cloud_product_warehouse_stock`.
- النشاط الجديد يحصل على فرع ومخزن افتراضيين، والمنتجات ترتبط بالمخزن الافتراضي تلقائيًا.
- أضيفت مفاتيح أجنبية مركبة تربط الفاتورة والحركة بالمخزن والفرع داخل النشاط نفسه.
- RPCs البيع والتسوية تقبل مخزنًا محددًا وتحدث رصيد المخزن وإجمالي المنتج ذريًا.
- اختبارات PostgreSQL تتحقق من عزل نشاطين ومن استقلال رصيد مخزن ثانٍ.
- **قيد حالي:** RPCs السحابية ما زالت تتعامل مع الكمية بوحدة صحيحة كاملة، بينما SQLite يخزن الألف. لا ترسل كميات SQLite إلى هذه RPCs قبل إتمام ترحيل وحدة القياس وتحديث العقود.

## 6. المبيعات والدفعات والمرتجعات

### المبيعات
- `cloud_sales`: النشاط، الفرع، المخزن، العميل الاختياري، المستخدم، الإجمالي، الخصومات، المدفوع، الحالة، `operation_id`، بصمة الطلب، التوقيت.
- `cloud_sale_items`: المنتج، `quantity_scaled`، سعر الوحدة، تكلفة الوحدة الملتقطة وقت البيع، الخصم، إجمالي البند.
- `cloud_sale_payments`: دفعات متعددة مرتبطة بالفاتورة، مع وسيلة الدفع والمبلغ والمرجع والفاعل.
- لا ينشأ دين دون عميل؛ الرصيد المستحق يحسب من دفتر العميل.
- لا يعاد حساب تكلفة بند البيع التاريخي من بطاقة المنتج بعد تغيير التكلفة.

### المرتجعات
- ترتبط بالفاتورة وبند البيع الأصلي.
- لا تتجاوز الكمية المتبقية القابلة للرد.
- تحفظ حالة الصنف ومصيره، ومبلغ الاسترداد، والمخزن الذي عاد إليه إن كان صالحًا.
- تنتج حركة مخزون عكسية وسجل دفعة استرداد داخل معاملة واحدة.
- الإلغاء لا يحذف الفاتورة؛ ينشئ أثرًا عكسيًا موثقًا.

## 7. المشتريات والموردون والعملاء والدفاتر

### المشتريات
- `cloud_suppliers`, `cloud_purchases`, `cloud_purchase_items`.
- فصل الطلب عن الاستلام والفاتورة عند الحاجة؛ تحديث المتوسط المرجح عند الاستلام الفعلي فقط.
- حفظ تكلفة الوحدة في بند الشراء، وعدم تعديل مستند تاريخي بصمت.
- مرتجع المورد يرتبط ببند الشراء الأصلي ويعكس المخزون والحساب.

### الدفاتر
- `cloud_customer_account_entries` و`cloud_supplier_account_entries` سجلات append-only.
- المديونية والمستحقات أرصدة مشتقة من القيود والدفعات والمرتجعات.
- لا يرسل العميل رصيدًا نهائيًا ليكتبه الخادم؛ الخادم يشتق الرصيد من الحركات الموثقة.
- تصحيح القيد المالي يكون بقيد عكسي أو تسوية مع سبب وفاعل واعتماد.

## 8. مطابقة المعرفات المحلية والسحابية

المعرف المحلي SQLite غالبًا integer auto-increment، بينما المعرف السحابي UUID. لا يجوز افتراض تساويها.

### المقترح
إنشاء جدول محلي `sync_entity_map` يحتوي:
- `entity_type`
- `local_id`
- `remote_id` UUID
- `business_id`
- `created_at`
- قيد فريد على `(entity_type, local_id)` وقيد فريد على `(business_id, entity_type, remote_id)`.

يُنشأ remote UUID عند أول مزامنة ناجحة أو يولد محليًا قبلها، ويحفظ الربط داخل معاملة محلية. كل سجل تابع لنشاط يحمل معرف النشاط السحابي المرتبط. لا يعاد استخدام معرف محلي من قاعدة مختلفة.

يجب تحديد سياسة merge/import عندما يستورد التاجر قاعدة موجودة إلى نشاط سحابي جديد؛ لا تربط بيانات نشاطين لمجرد تشابه الاسم أو SKU.

## 9. Outbox والمزامنة

### جدول Outbox المحلي المقترح
- `operation_id` UUID فريد.
- `business_id` و`entity_type` و`operation_type`.
- `payload_json` بإصدار مخطط.
- `created_at`, `attempt_count`, `next_attempt_at`.
- `status`: pending / sending / synced / blocked / failed.
- `last_error_code` دون بيانات سرية.
- `depends_on_operation_id` أو قائمة اعتماديات عند إنشاء كيان يعتمد على كيان جديد.

### إيصال الخادم
- جدول `cloud_operation_receipts` بمفتاح فريد `(business_id, operation_id)).
- بصمة الحمولة والنتيجة ومعرفات السجلات المنشأة والتوقيت.
- إعادة الطلب بنفس البصمة تعيد النتيجة السابقة.
- نفس المعرف ببصمة مختلفة يرفض مع خطأ واضح.

### دورة المزامنة
1. تنشأ العملية المحلية ومعرفها في معاملة SQLite واحدة مع التغيير المحلي وإضافة Outbox.
2. يقرأ عامل المزامنة العمليات المعلقة حسب الاعتماديات والترتيب.
3. يرسل العملية إلى RPC موثوق؛ لا يكتب صفوف المخزون أو الفواتير مباشرة.
4. الخادم يتحقق من العضوية والصلاحية والنطاق ويطبق العملية داخل معاملة واحدة.
5. يحفظ إيصال العملية والبصمة والنتيجة.
6. يعلّم العميل العملية synced ويحفظ remote IDs داخل معاملة محلية.
7. يسحب العميل التغييرات السحابية بمؤشر cursor، مع معالجة الحذف المنطقي والتعديلات حسب إصدار الكيان.
8. عند انقطاع الشبكة، تبقى العملية pending وتُعاد بأمان مع backoff.

## 10. قواعد فض التعارض

| نوع البيانات | السياسة |
|---|---|
| البيع/الشراء/الدفعات/المرتجعات | عمليات append-only ذرية؛ لا استبدال تلقائي |
| أرصدة المخزون | مشتقة من حركات معتمدة؛ قفل وتسلسل خادمي |
| تحويل مخزون | مستند واحد ينشئ خروجًا ودخولًا متوازنين |
| اسم/وصف المنتج | مراجعة إصدار؛ يمكن قبول تعديل غير متعارض أو طلب حل يدوي |
| السعر والتكلفة | صلاحية وتدقيق؛ لا يكتب آخر جهاز فوق قيمة أحدث دون كشف التعارض |
| إعدادات النشاط | نسخة revision؛ تعديل المالك أو مفوضه فقط |
| الصلاحيات والعضويات | Online-only عبر RPCs مدققة؛ لا مزامنة offline لتغيير صلاحية حساب |
