## 1. الخلاصة التنفيذية

المشروع تجاوز مرحلة النموذج الأولي البسيط: توجد الآن وظائف محلية لإدارة المنتجات والمخزون والفروع والمخازن والمبيعات والمشتريات والموردين والعملاء والمصروفات، مع اختبارات Flutter ونسخ احتياطي واستعادة. كما توجد بنية Supabase أولية للمستخدمين والصلاحيات وبيانات سحابية محدودة، وأضيفت اختبارات PostgreSQL أولية لعزل الأنشطة والتحكم في الصلاحيات ومنع بعض التغييرات غير الموثقة.

لكن المنتج **ليس جاهزًا تجاريًا**. السبب الأساسي ليس غياب بعض الشاشات، بل أن قاعدة البيانات المحلية والسحابية لم تتكاملا بعد، ولا يوجد تسجيل دخول فعلي داخل التطبيق أو مزامنة متعددة الأجهزة أو لوحة مراقبة للمالك. كما أن تغطية RLS واختبارات أمان API لا تزال جزئية.

## 2. الوظائف المحلية الموجودة

بحسب README وخارطة الطريق والاختبارات الحالية:

- المنتجات والتصنيفات ووحدات القياس.
- فروع ومخازن متعددة محليًا، مع أرصدة منفصلة.
- تسويات وتحويلات المخزون مع سجل حركات ومعاملات.
- مبيعات متعددة الأصناف، واختيار المخزن، وحفظ الفاتورة والبنود وتحديث المخزون ذريًا.
- ربط البيع بالعميل وتسجيل المدفوع والمتبقي.
- إدارة الموردين وفواتير مشتريات متعددة الأصناف واستلام المخزون.
- تحديث متوسط التكلفة المرجح عند الاستلام وتسجيل التزامات المورد والمدفوعات.
- إدارة العملاء والمقبوضات وكشوف الحساب الأساسية.
- تسجيل المصروفات وملخص مالي أولي.
- تصدير CSV.
- نسخ SQLite احتياطية متسقة باستخدام `VACUUM INTO` واستعادة مخططات 3 إلى 9 مع تحقق واستبدال ذري.

وجود هذه الوظائف محليًا لا يعني أنها متاحة عبر السحابة أو أنها اجتازت اختبار تشغيل ميداني.

## 3. ما أُنجز في أساس الأمان السحابي

### الهجرات والبيانات
- جداول الأنشطة التجارية والعضويات والصلاحيات وسجل التدقيق.
- سياسات RLS ومساعدات تحقق من العضوية والملكية والصلاحيات.
- جداول سحابية أولية للمنتجات والمخزون والمبيعات وبنود البيع والمصروفات.
- عمليات خادمية للمبيعات وتسويات المخزون مع معرفات عمليات لمنع التكرار.
- دالة Edge Function أولية لإنشاء مستخدم باسم مستخدم وكلمة مرور دون دعوة بريد إلكتروني.
- فشل إنشاء العضو إذا تعذر حفظ سجل التدقيق المطلوب.
- إجراء PostgreSQL ذري لتحديث صلاحيات العضو مع حدث تدقيق قبل/بعد، ومنع المدير المفوض من منح صلاحية لا يملكها أو تغيير صلاحيات المالك.
- تعويض فشل إنشاء العضو fail-closed: لا تُهمل أخطاء تنظيف العضوية أو مستخدم Auth، ويُعطّل العضو كإجراء احتياطي عند فشل الحذف.

### تحسينات الحماية المضافة
- تعطيل الحذف المباشر لمصروفات السحابة؛ التصحيح المالي يجب أن يكون عبر مسار عكس موثق.
- منع العميل من تعديل العضويات والصلاحيات وسجل التدقيق مباشرة؛ هذه الكتابات محصورة بالخدمات الخادمية الموثوقة.
- ربط معرفات عمليات البيع وتسوية المخزون ببصمة حمولة الطلب؛ إعادة إرسال الطلب نفسه تعيد النتيجة، أما استخدام المعرف نفسه مع حمولة مختلفة فيُرفض.
- إضافة قفل معاملاتي على معرف العملية لتسلسل محاولات الإعادة المتزامنة.

### اختبارات PostgreSQL الحالية
التشغيل الناجح: https://github.com/ashraf18275/smart-merchant-suite/actions/runs/41741288175  
الالتزام الذي اختُبر: `e8c9f3e02534c5bebebe0f949fc3fef8b64f144a`.

تغطي الاختبارات:
- عزل بيانات نشاطين تجاريين.
- عدم ظهور بيانات الأنشطة لغير أعضائها.
- منع العضو غير النشط من الوصول حتى مع وجود سجل صلاحية.
- عضو يملك `products.view` يستطيع القراءة ولا يستطيع إنشاء بيع دون `sales.create`.
- منع التعديل المباشر لرصيد المخزون وإدراج المبيعات.
- منع الحذف المباشر للمصروفات.
- منع العميل من إدراج أو تعديل أو حذف العضويات والصلاحيات وسجلات التدقيق.
- إعادة إرسال البيع بالمعرف والحمولة نفسيهما دون خصم المخزون مرتين.
- رفض إعادة استخدام معرف العملية مع حمولة بيع أو تسوية مخزون مختلفة، وتحديث الصلاحيات مع تسجيل تدقيق واختبار منع تصعيد الصلاحيات.

هذه اختبارات أمن وانحدار أولية على PostgreSQL تجريبي. لا تمثل اختبار اختراق أو مراجعة أمنية مستقلة، ولا تثبت سلامة كل الجداول والسياسات والدوال.

## 4. فجوات حرجة قبل ربط التطبيق بالسحابة

### أ. لا يوجد تكامل Supabase داخل Flutter
- `pubspec.yaml` لا يتضمن عميل Supabase.
- لا توجد شاشة دخول فعلية أو إدارة جلسات أو استعادة حساب.
- أداة تحويل اسم المستخدم إلى هوية Auth داخلية مجرد تحقق محلي، وليست تسجيل دخول.
- لا توجد واجهة لإضافة المستخدمين وتعيين الصلاحيات من التطبيق.
- لا توجد واجهة لتعديل صلاحيات عضو أو تعطيله من خلال مسار خادمي مدقق.

### ب. فجوة بين نموذج SQLite والنموذج السحابي
المخزون المحلي يدعم الفروع والمخازن، بينما النموذج السحابي الحالي يقتصر على `business_id` ولا يعرّف بعد الفروع والمخازن أو أرصدتها المنفصلة. كما لا يغطي السحاب بعد العملاء والموردين والمشتريات والمدفوعات والمرتجعات وورديات الصندوق. لذلك لا يجوز بدء مزامنة عامة قبل تصميم نموذج سحابي متوافق مع قواعد المجال المحلية.

### ج. المزامنة لم تُنفذ
- لا يوجد Outbox محلي متكامل.
- لا يوجد مزامنة فعلية بين Windows وAndroid.
- لا توجد سياسة تعارض لكل كيان أو إعادة محاولة end-to-end.
- لا توجد مراقبة عن بُعد أو حالة أجهزة.

### د. تدقيق وأمان إضافيان مطلوبان
- اختبارات RLS لكل جدول وعملية ولكل نوع مستخدم.
- اختبارات Edge Function فعلية تشمل عدم المصادقة، وعضو غير موجود، وصلاحيات مفوضة، وتصعيد الصلاحيات، واسم مستخدم مكرر، وفشل سجل التدقيق وفشل التعويض.
- مراجعة سلوك التنظيف التعويضي في `create-member`؛ يجب ألا تُهمل أخطاء حذف العضوية أو مستخدم Auth عند فشل العملية.
- مراجعة CORS عند إضافة عميل ويب؛ ترويسة `*` الحالية ليست بديلًا عن المصادقة أو التفويض.
- مراجعة حدود معدل الطلبات وسياسة كلمات المرور واستعادة الحساب وإبطال الجلسات والأجهزة.
- مراجعة خارجية مستقلة قبل استخدام بيانات متاجر حقيقية.

## 6. القرارات والمخاطر المعروفة

- يجب أن يطابق النموذج السحابي نموذج الأعمال المحلي قبل إطلاق المزامنة.
- لا يُسمح بحذف الأثر المالي أو المخزني بصمت.
- يجب أن تكون معرفات العمليات idempotent ومقيدة ببصمة الحمولة، ثم تُختبر عبر Outbox وإعادة الإرسال من أجهزة حقيقية.
- الصلاحيات يجب أن تُفرض في الخادم، مع استخدام فحص العميل لإخفاء عناصر الواجهة فقط.
- عدد المستخدمين غير محدود كقرار منتج، لكن يجب مراجعة قيود Supabase والتكلفة والأداء قبل التسويق بهذا الوعد.
- أسماء المستخدمين السحابية فريدة عالميًا حاليًا بسبب ربطها بمعرف Auth اصطناعي؛ يجب إبقاء هذا القيد واضحًا أو إعادة تصميم تسجيل الدخول قبل السماح بتكرار الاسم بين الأنشطة.
- لا توجد ضريبة أو فاتورة ضريبية في النطاق الحالي؛ يلزم تقييم قانوني ومحاسبي للسوق المصري قبل البيع.
- لا تستخدم بيانات متجر حقيقية قبل إكمال الأمان والمزامنة والنسخ الاحتياطي واختبارات الأجهزة.

التنفيذ الحالي:
- كل نشاط قائم يحصل على فرع ومخزن افتراضيين، وكل نشاط جديد ينشئهما trigger خادميًا.
- المنتجات الجديدة ترتبط بفرع ومخزن افتراضيين، وينشأ لها رصيد مخزني منفصل.
- أضيفت جداول الفروع والمخازن وأرصدة المنتج لكل مخزن.
- أضيفت مراجع الفرع والمخزن إلى فواتير البيع وحركات المخزون مع مفاتيح أجنبية مركبة تمنع الربط عبر نشاط آخر أو فرع آخر.
- أصبحت عمليات البيع والتسوية السحابية تقبل مخزنًا محددًا، وتحدث رصيد المخزن وإجمالي المنتج في معاملة واحدة.
- بقيت واجهات Flutter والمزامنة غير موصلة. كما أن الكمية السحابية ما زالت بوحدة القطعة الكاملة في هذه المرحلة؛ يجب تحويلها إلى وحدة الألف قبل المزامنة لأن SQLite يستخدم thousandths.
