# عزل قاعدة SQLite لكل نشاط

**قرار المنتج المعتمد:** لكل نشاط سحابي ملف SQLite مستقل على كل جهاز.

## سلوك التطبيق

- يظل ملف قاعدة البيانات المحلي القديم `smart_merchant_suite.db` كما هو ويظل متاحًا للوضع المحلي دون نشاط سحابي.
- عند فتح مساحة نشاط سحابي واختيار «فتح بيانات هذا النشاط على الجهاز»، يفتح التطبيق قاعدة جديدة داخل مجلد `businesses` باسم مشتق من UUID النشاط بعد تطبيعه إلى lowercase.
- لا يقبل مولّد المسار إلا UUID بالصيغة القياسية؛ لا يمكن استخدام اسم نشاط أو نص حر أو مسار ملف كمعرّف.
- كل نشاط له ملف مستقل، وجداول المنتجات والمبيعات والمشتريات والعملاء والموردين والمخزون والحسابات والصندوق والنسخ الاحتياطي الخاصة به لا تتشارك الصفوف مع نشاط آخر.
- عند أول فتح لقاعدة النشاط، ينشئ التطبيق المخطط المحلي الحالي كاملًا. ويثبت `database_business_id` داخل `sync_metadata`. إذا وُجد ملف يحمل هوية نشاط مختلفة، يرفض التطبيق فتحه بدل المخاطرة بعرض بيانات مستأجر آخر.
- لا يتم إنشاء ملف قاعدة النشاط إلا عند فتح بيانات النشاط، وليس بمجرد تسجيل الدخول أو عرض الكتالوج السحابي.

## حماية البيانات القديمة

- لا تُنسخ قاعدة `smart_merchant_suite.db` القديمة إلى أي نشاط.
- لا يتم استنتاج النشاط الذي تنتمي إليه البيانات التاريخية من الاسم أو الفرع أو SKU أو التوقيت.
- تبقى البيانات القديمة في وضعها المحلي حتى تُنفذ لاحقًا أداة استيراد/ربط صريحة ذات معاينة ومراجعة، ولا يجوز تشغيلها دون موافقة صاحب النشاط.
- لا توجد مزامنة Push/Pull في هذه المرحلة، ولا يتم إرسال أي صف محلي إلى Supabase.

## النسخ الاحتياطي والاستعادة

- النسخ الاحتياطي يظل محصورًا في قاعدة النشاط المفتوحة حاليًا؛ لا يجمع بيانات عدة أنشطة في ملف واحد.
- تم تصحيح إصدار التوافق إلى SQLite schema v18.
- عند استعادة بيانات نشاط، تُحذف أحداث Outbox والتعارضات وخرائط المعرفات والمؤشرات القديمة داخل نفس معاملة الاستعادة؛ لأن معرفات SQLite قد تتغير أو تُستبدل.
- تبقى بيانات تعريف الجهاز وربط ملف القاعدة بهوية النشاط في `sync_metadata` ولا تُستبدل ببيانات النسخة.
- هذا يمنع إرسال أحداث قديمة أو استعمال خرائط محلية أصبحت تشير إلى سجلات أخرى بعد الاستعادة.

## حدود المرحلة

- تم ربط زر فتح بيانات النشاط بمسار قاعدة النشاط المستقلة.
- لا تزال الفروع والمخازن المحلية ذات معرفات SQLite مستقلة عن معرفات الفروع والمخازن السحابية UUID. لا يوجد ربط تلقائي بينهما.
- لا يتم نقل البيانات المحلية القديمة إلى النشاط الجديد.
- لا تعمل المزامنة حتى تكتمل طبقة RPC idempotency وسجل تغييرات Pull واختبارات جهازين.
- لا يعتبر نجاح بناء التطبيق أو إنشاء ملف قاعدة جديد دليلًا على اكتمال المزامنة أو الجاهزية التجارية.

## الاختبارات المطلوبة

- مساران مختلفان لنشاطين مختلفين.
- تطبيع UUID قبل اشتقاق اسم الملف.
- رفض المعرفات غير القياسية ومحاولات path traversal.
- تثبيت هوية قاعدة البيانات ورفض إعادة فتحها بهوية نشاط آخر.
- الاستعادة تمسح Outbox والخرائط والمؤشرات والتعارضات القديمة وتحتفظ بهوية النشاط وdevice ID.
- اختبار إنشاء قاعدتين فعليتين والتحقق من عدم ظهور صفوف النشاط A داخل قاعدة النشاط B قبل تمكين أي مزامنة.


## سياق النشاط والفرع والمخزن

- اختيار الفرع والمخزن السحابي محفوظ لكل مستخدم ونشاط، ولا يختلط عند التبديل بين حسابات أو أنشطة.
- قبل فتح بيانات SQLite للنشاط، يجب أن توجد خريطتا ربط صريحتان للفرع والمخزن في sync_entity_map ضمن business_id نفسه.
- يتحقق التطبيق من هوية قاعدة النشاط ومن نشاط الفرع والمخزن ومن تبعية المخزن للفرع. ثم يحول UUIDs السحابية إلى أرقام SQLite المحلية فقط عبر الخرائط.
- تمرر أرقام الفرع والمخزن المحلية المختارة إلى شاشات المبيعات والمشتريات وإدارة الفروع والمخازن. عند غياب الربط أو عدم اتساقه لا يُستخدم المخزن الرئيسي كبديل.
- الربط يدوي ومؤكد، ولا ينقل أي سجل أو رصيد ولا يشغّل المزامنة.
- مسار ترقية قاعدة البيانات موحد الآن بين Android وWindows حتى الإصدار 18، مع اختبار للترقية من الإصدار 16 إلى 18.
